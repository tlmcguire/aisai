# W14 — Transitive coverage and lockfiles

**Goal:** every project and every downloaded package gets a complete transitive tree, with the
chain from the root to each vulnerable package, whatever lockfile or manifest format it uses.

**Status:** ⬜ not started
**Depends on:** W1
**Blocks:** W11 (reachability needs the full tree), W13 (historical trees use the same graph model)

## Current state (verified 2026-11-23, from the root README)

- Read: `Cargo.lock`, `package-lock.json`, `poetry.lock`, `Pipfile.lock`, `go.mod`, pinned
  `requirements*.txt`.
- Not read: `yarn.lock`, `pnpm-lock.yaml`, `uv.lock`.
- `go.mod` and `Pipfile.lock` record no tree, so every indirect package hangs directly off the
  root and the chain is one name long.
- For npm and cargo downloads, when deps.dev cannot answer, only the root package is scanned.
- Dependencies given as git or path sources, or as version ranges, are skipped in advisory
  matching.

## Tasks

### Lockfile parsers
- [ ] `yarn.lock` classic (v1) parser, with its own fixtures
- [ ] `yarn.lock` Berry (v2+) parser, with its own fixtures
- [ ] `pnpm-lock.yaml` parser for lockfile versions 6 and 9, including `importers` and peer
      suffixes
- [ ] `uv.lock` parser, including source and marker fields
- [ ] For each parser: a fixture generated by the real tool, and a test that the resulting tree
      matches the tool's own `list` output

### Trees where none are recorded
- [ ] `go.mod`: build the tree from the module graph (`go mod graph` logic, read-only, no network
      beyond the module proxy that W16 will add). Mark any edge that was inferred as inferred
- [ ] `Pipfile.lock`: derive the tree from the `_meta` and each package's declared requirements,
      using the same metadata that PyPI provides for each pinned version
- [ ] Record for each edge whether it came from a lockfile, a manifest, or a registry

### Fallback resolution
- [ ] npm: when deps.dev fails, resolve the tree from the registry packuments (the same data W13
      reads), with a visible note in the graph that the tree is resolved locally
- [ ] Cargo: the same fallback, from the crates.io index
- [ ] Keep the existing "only the root is scanned" behaviour as the last resort, and make the
      graph say which of the three levels was used

### Non-registry and range dependencies
- [ ] Git and path dependencies: record them as nodes with source `git` or `path`; scan their
      code when present in the project; never query advisories for them by version
- [ ] Ranges: where a lockfile is absent, resolve each range to the best matching version and mark
      the node `resolved from range`
- [ ] Show the unresolved ones in a list so they are not silently dropped

### Multiple versions
- [ ] Graph node identity uses PURL with version (the W-plan decision D10), so two versions of one
      package are two nodes and a conflict is visible. Check that this is true today for lockfile
      trees, and fix it where it is not

### Advisory matching
- [ ] Re-run advisory matching for every new node created by this work
- [ ] Report how many nodes were skipped and why (git, path, unresolved range)

## Acceptance criteria

- [ ] A `yarn.lock`, a `pnpm-lock.yaml` and a `uv.lock` fixture each produce a tree with the same
      node count and edges as the tool's own listing
- [ ] A `go.mod` fixture shows indirect packages under their real parents, with inferred edges
      marked
- [ ] An npm download with deps.dev disabled still produces a full transitive tree with a note
- [ ] Two versions of one package in a tree appear as two nodes

## Notes

- Lockfile parsing is the cheapest route to a complete tree, so it should come before the
  historical work in W13.
- The chain in the UI (`chrono → time`) only helps if the tree under it is complete. This
  workstream is what makes that chain trustworthy.
